BNN-train-infer · 硬件后端笔记 / 01

同一条 API，
换一颗心脏。

项目最近加入了 bnn-hw 的 SystemVerilog 计算核心，以及一条 Verilator 软硬件协同仿真链路。这一篇只回答一个问题：bnn-accelerator 这一层，是怎么从 C 软件实现切到仿真器实现的？

构建期选择 C ABI 不变 整数点积交给 RTL FP32 后处理留在 C
ONE-LINE ANSWER

没有运行时 dispatch。切到 Verilator 后，链接进静态库的 BNN_* 符号换成了另一份实现；设备句柄里多挂一个仿真器，BNN_Execute 把整数点积交给桥接层，桥接层再逐周期驱动 RTL。

ACCE=softsoft-bnn-accelerator.c
ACCE=verilatorverilator-bnn-accelerator.c
+ bridge.cpp + Vbnn_core_top

两层之上：bnn-infer、BNNE 引擎和模型代码完全无感。

01 / 08

先给结论：切换发生在 make，不在运行期

整个仓库里，应用、引擎和模型只认识 bnn-accelerator.h 这一层 C 接口。所谓“切到仿真器”，不是给程序加一个 --backend 开关，而是在构建时把实现这一层接口的那个翻译单元换掉，再额外链接桥接层与 Verilator 生成的模型。

POINT 01

构建期二选一

ACCE=soft 编译 soft-bnn-accelerator.c；ACCE=verilator 编译 verilator-bnn-accelerator.c，并加入桥接层、Verilator 运行库和 RTL 模型。两个后端不会同时进入同一个可执行文件。

POINT 02

句柄内部换零件

公共类型仍是 BNN_Device 这种不透明指针。仿真后端的 struct bnn_accel_device 只是多了一个 BNN_RtlSim* sim，调用者看不到，ABI 也不变。

POINT 03

算术分工，语义不换

RTL 只算整数分组点积 D[n][g]；GEMV/GEMM 的 FP16 scale 转换与按组 FP32 累加仍在 C 中完成。这样两后端的输出可以逐字节一致。

同一个二进制里不会出现两条路径。上面的切换只用于对照阅读；真正决定产物的是 make ACCE=...。

最关键的一句话：引擎从未“发现”后端变了。它仍然按 DeviceOpen → GetCaps → BufferAlloc → BufferWrite → Execute → BufferRead 的顺序调用；变化的只是这些符号背后最终执行的是 C 代码，还是一条 Verilator 仿真链路。

02 / 08

先看不变的部分：一条很薄的 C ABI

能换得这么干净，是因为分界线划得很窄。上层不拥有“设备”的内部结构，只持有一个不透明句柄；所有生命周期、内存和计算都通过固定签名的函数进入加速器层。

这段代码在两种构建下完全相同。模型层只关心 GEMV/GEMM 的语义，不关心设备是谁。

数值契约也必须相同。公共头文件规定：FP16 scale 精确转成 FP32；每组乘积单独舍入；按组索引递增做 FP32 累加；禁用 FMA 与 fast-math；舍入模式必须是 FE_TONEAREST，并保留次正规数。两个后端各自保留了同名、同实现的 HalfToFloat、FloatMultiply、FloatAdd，这是后面逐字节对比能成立的前提。

CAPS

能力上报一致

两个后端的 BNN_DeviceGetCaps 都报告 max_in/out_features = 4096、group_size = 128、支持 GEMV/GEMM/DOT_GROUPS。引擎启动时只检查 api_version、group_size、max_rows，因此不会产生分支。

ABI

同名符号，不同实现

顶层构建只把其中一份 *-bnn-accelerator.o 放进归档。链接器解析 BNN_Execute 等符号时，只可能命中一份。没有函数指针表，也没有运行时注册。

TEST

同一个测试对象

差分测试把 tests/accelerator/test_bnn_accelerator.c 只编译一次，然后分别链接软件实现和 Verilator 归档。同一份 C 调用方代码、同一组断言，最后比较两边的输出字节。

节选并加了分段注释。原始顺序见 Makefile:1-62。核心是第 26 行：$(ACCE)-bnn-accelerator.c 把“后端选择”变成了“选哪个文件参与编译”。

  1. 1

    选文件名

    soft → soft-bnn-accelerator.c；verilator → verilator-bnn-accelerator.c。两个文件导出同一组 BNN_* 符号，所以上层源码不需要改。

  2. 2

    隔离构建目录

    产物分别落在 build/soft/ 与 build/verilator/。切换时不会把上一后端的 .o 混进新归档；根目录的 bnn-infer 是 phony 目标，每次都会重新链接。

  3. 3

    生成 RTL 模型

    verilator --cc --assert --trace --top-module bnn_core_top ... 把 bnn-hw/bnn_core/*.sv 转成一个 C++ 类 Vbnn_core_top，再编译成 Vbnn_core_top__ALL.a。

  4. 4

    桥接与运行库一起入档

    桥接层用 C++17 编译；Verilator 的 verilated.cpp、verilated_threads.cpp、verilated_vcd_c.cpp 也进入归档。最终用 ar -M 把生成的 RTL 归档展开合并进来，嵌入方仍然只需链接一个 .a。

  5. 5

    换链接器，改测试驱动

    最终链接从 CC 改为 CXX，并附加 -pthread -latomic -lm。测试脚本也改成“C 源单独编译成 .o，再用 C++ 链接器链接归档”，否则 C 测试程序无法拉入 C++ 对象。

同一个 API 调用，在两种后端里实际做什么

公共调用ACCE=softACCE=verilator
BNN_DeviceOpen 校验设备号/浮点格式，calloc 一个设备。 同样校验，再调用 bnn_rtl_create 建 context、模型并复位。
BNN_MatrixCreate 校验尺寸/scale，malloc 并复制权重与 scale 到主机内存。 校验逻辑相同；也复制到主机内存。没有持久化的“设备权重内存”，权重每次任务由桥接层流式送入。
BNN_BufferAlloc
BNN_BufferWrite/Read		 主机 malloc + memcpy。 完全相同。仿真后端用主机内存模拟设备缓冲语义。
BNN_Execute 逐行调用 ComputeRow，全部算术在 CPU。 逐行调用 bnn_rtl_dot_groups；RTL 算整数点积，返回后用 StoreRow 做 FP32 后处理。
BNN_DeviceClose 检查无存活资源后 free。 检查无存活资源后销毁仿真器（结束 VCD），再 free。

这不是总线级仿真。仿真后端的“设备内存”仍是主机堆内存；MatrixCreate 不会把权重烧进 RTL，BufferWrite 也不会触发 DMA。真正跨过软件/硬件边界的，只有 Execute 期间桥接层逐周期送给 RTL 的激活与权重位。这是功能性协同仿真，用来验证算术与接口时序，不建模总线延迟和存储带宽。

为什么浮点不一起放进 RTL？

当前的 bnn_core_top 是纯整数核心：它没有 FP16 scale 输入，也没有浮点乘法/累加单元。与其在 RTL 里新造一套浮点路径，不如把“整数点积”这个清晰的边界交给硬件，把公共 API 要求的 FP32 后处理继续留在 C 中。

更重要的是，这样能复用与软件后端完全相同的 HalfToFloat、FloatMultiply、FloatAdd 实现。RTL 的整数结果只要与软件公式一致，最终输出就能做到逐字节相同，而不是“数值上接近”。

verilator-bnn-accelerator.c:350-383 · StoreRowC
if (operation == BNN_OP_DOT_GROUPS) {
    memcpy(y, dots, dot_bytes);
    return;
}

for (n = 0; n < matrix->out_features; ++n) {
    float acc = 0.0f;
    for (g = 0; g < matrix->groups; ++g) {
        size_t index = (size_t)n * matrix->groups + g;
        int32_t dot;
        uint16_t scale_bits;
        memcpy(&dot, (const unsigned char*)dots
               + index * sizeof dot, sizeof dot);
        memcpy(&scale_bits, (const unsigned char*)matrix->scale_fp16
               + index * sizeof scale_bits, sizeof scale_bits);
        scale = HalfToFloat(scale_bits);
        term  = FloatMultiply(scale, (float)dot);
        acc   = FloatAdd(acc, term);
    }
    memcpy(y + (size_t)n * sizeof acc, &acc, sizeof acc);
}

一个容易忽略的边界：RTL 核心本身支持完整 int8 范围，包括 -128；但公共 API 规定输入必须落在 [-127, 127]。因此 verilator 后端在进入桥接层之前，就已经逐行拒绝 INT8_MIN，和软件后端保持完全相同的错误语义。桥接层自己的测试则明确覆盖了 -128，证明限制来自 API 层，而不是 RTL 算不了。

dots 缓冲区在行循环外只分配一次，所有行和所有操作复用；对 GEMM 来说，每行一次桥接调用，但不会每行重新分配结果缓冲。

06 / 08

桥接层：把一次函数调用拆成一个个时钟周期

这是整条链路里最“硬件”的部分。桥接层同时扮演三个角色：命令发起者、激活/权重供数者、结果接收者。它每拍驱动一次 Verilator 模型，直到最后结果满足 res_valid && res_ready && res_last 并推进该握手上升沿；这是核心唯一的成功完成事件。

建一个属于本设备的仿真器

DeviceOpen

BNN_DeviceOpen 通过公共校验后，verilator 后端调用 bnn_rtl_create。桥接层创建 VerilatedContext（单线程），构造生成的 Vbnn_core_top，可选打开 VCD，然后把核心复位。

  • 每个 BNN_Device 拥有自己的 context 和模型，互不共享状态。
  • 桥接层撤销命令与共用输入 valid、清空驱动数据并拉低结果 ready，再以高有效同步 reset 推进两个时钟周期。核心在有效沿清空全部锁存配置、计数和数据有效位；reset 置位期间屏蔽所有握手，无取消通知。

context.threads(1);

把权重放进矩阵对象

MatrixCreate

BNN_MatrixCreate 的校验逻辑与 soft 基本相同：检查尺寸、group_size == 128、scale 不含 NaN/Inf、weight_bytes 与 scale_count 精确匹配，然后把数据复制到矩阵自己持有的主机内存。

  • 此时没有“下载到设备”的动作；RTL 核心没有权重存储器。
  • 真正送权重发生在每次 Execute：桥接层按通道、按 32 元素块流式发送。

发命令：K / G / N 变成三个计数字段

桥接层提交前保证三个尺寸非零、K/G 整除且 groups≤256；核心仅保留仿真 assert，不产生运行时错误码。先确认核心处于 idle 且 cmd_ready 为 1，再写入三个尺寸，并保持 cmd_valid 到命令握手沿；该沿锁存尺寸并启动任务。结果通道提前置 res_ready。

流式喂数：每拍 32 个 k

act / weight

命令被接收后，桥接层以 in_valid 同时声明激活和权重有效，并在 in_ready 允许时通过一次共用握手推进 32 个 k：32 个激活（8 个 32-bit word）和 32 个权重位（1 个 32-bit word）。没有双输入独立握手；阻塞期间必须保持 valid 和两份数据。

  • 流是通道优先：先送完 channel 0 的全部 block，再送 channel 1。
  • 同一组激活会在每个输出通道重放一次，因为核心没有内部激活缓存。
  • cmd_k_blocks/cmd_group_div 与已握手拍数决定通道和逻辑组边界，输入没有 last。

收结果：N × groups 个 int32

res / last

结果按 [channel][group] 顺序返回。桥接层用 received 计数校验组号与边界标志，把 res_data 逐个复制到 dots。仅在最后结果满足 res_valid && res_ready && res_last 且推进握手沿后，核对收发数量及 cmd_ready 后返回成功，不额外等待完成周期；无独立完成通道或 res_error。

const bool task_complete =
    core.res_valid && core.res_ready && core.res_last;

    if (received >= result_count ||
        core.res_group_idx != received % groups ||
        bool(core.res_chan_last) != (received % groups == groups - 1) ||
        bool(core.res_last) != (received == result_count - 1))
        return recover(sim, BNN_EIO);
    const uint32_t bits = core.res_data;
    std::memcpy(output + size_t(received), &bits, sizeof bits);
    ++received;

        return recover(sim, BNN_EIO);
    core.cmd_valid = 0;
    core.in_valid = 0;
    core.eval();
    sim->flush_trace();
    return BNN_OK;
}

6.1

一拍里到底装了什么

RTL 的 32 条 lane 一次处理 32 个 k 位置。桥接层把连续的 4 个 int8 塞进一个 32-bit word，共 8 个 word；权重则按位打包成一个 32-bit word，bit i 对应 lane i。

act[0]k0–k34 × int8
act[1]k4–k74 × int8
act[2]k8–k114 × int8
act[3]k12–k154 × int8
act[4]k16–k194 × int8
act[5]k20–k234 × int8
act[6]k24–k274 × int8
act[7]k28–k314 × int8
weight_data[31:0]bit i = W[n][k0+i]，1 → +1，0 → −1

激活按字节小端拼装（byte 0 落在 bit 0..7）；权重按位平铺。两者共用 in_valid/in_ready，在同一个上升沿同时消费，不能单独握手。

const size_t channel = size_t(sent / blocks);
const size_t offset  = block * 32;

for (unsigned word = 0; word < 8; ++word) {
    uint32_t packed = 0;
    for (unsigned byte = 0; byte < 4; ++byte)
        packed |= uint32_t(uint8_t(input[offset + word * 4 + byte]))
                  << (byte * 8);
    core.act_data[word] = packed;
}

const size_t weight_offset =
    channel * (in_features / 8) + block * 4;
uint32_t packed = 0;
for (unsigned byte = 0; byte < 4; ++byte)
    packed |= uint32_t(weights[weight_offset + byte]) << (byte * 8);
core.weight_data = packed;
6.2

通道优先，以及“激活重放”

核心一次命令只处理“一个输入向量 × N 个输出通道”。它没有内部激活缓存，因此桥接层必须按输出通道重复送同一组激活。总拍数不是 K/32，而是 (K/32) × N。

channel 0
block 0block 1…block B−1
channel 1
block 0block 1…block B−1
…
同一组 X，再送一遍
channel N−1
block 0block 1…block B−1

B = K / 32。输入无 last 信号；核心按每次 in_valid && in_ready 推进计数。每 B 拍形成通道边界，每 cmd_group_div 拍形成逻辑组边界；尺寸仅在命令握手沿锁存。

为什么这个细节重要？如果只按 K/32 送数，只会算完一个输出通道。真实加速器通常会在设备侧缓存激活；当前这个核心明确把重放责任交给外层。README 也把“不要直接把重放变成重复主机上传”列为后续设备调度层要优化的事情。

6.3

逐周期循环与握手

桥接层的主循环可以概括为：准备本拍输入 → eval() → 采样握手 → tick() 推进一个 10 ns 周期。只有命令、共用输入、结果三个 ready/valid 通道。核心状态为 IDLE → RUN（收数）→ DRAIN（等最后结果握手）→ IDLE；保留 status_idle/status_busy，最后结果握手的同一沿不能接新命令，下一上升沿才可接收。

通道桥接层动作完成条件
cmd_valid/cmd_ready写 cmd_k_blocks/cmd_group_div/cmd_out_chans，保持 valid 不撤销cmd_valid && cmd_ready 同拍为 1
in_valid/in_ready
act_data / weight_data		按通道和 block 配齐两个操作数；阻塞时保持 valid 和两份数据一次共用握手同时接收激活和权重，无输入 last
res_valid/res_readyres_ready = 1；校验组号、通道末标志、全局末标志唯一成功完成为 res_valid && res_ready && res_last 握手沿，且结果总数匹配
status_idle/status_busycmd_ready 决定能否发命令；status_idle/status_busy 仅为状态输出，不是额外握手通道RUN/DRAIN 为 busy，最后结果握手后回 IDLE，下一沿才可接新命令
verilator-bnn-bridge.cpp · 主循环骨架（节选）C++
uint64_t sent = 0, received = 0;
bool accepted = false;
core.res_ready = 1;
for (uint64_t cycle = 0; cycle < max_cycles; ++cycle) {
    core.cmd_valid = !accepted;
    core.in_valid = accepted && sent < input_beats;
    if (core.in_valid) { /* 按 sent 打包两份数据；阻塞时 sent 不变 */ }

    core.eval();
    if (sim->context.gotFinish()) return recover(sim, BNN_EIO);

    const bool cmd_fire = core.cmd_valid && core.cmd_ready;
    const bool in_fire = core.in_valid && core.in_ready;
    const bool res_fire = core.res_valid && core.res_ready;
    const bool task_complete = res_fire && core.res_last;

    if (res_fire) { /* 校验并收集握手前的结果负载 */
        if (received >= result_count ||
            core.res_group_idx != received % groups ||
            bool(core.res_chan_last) != (received % groups == groups - 1) ||
            bool(core.res_last) != (received == result_count - 1))
            return recover(sim, BNN_EIO);
        const uint32_t bits = core.res_data;
        std::memcpy(output + size_t(received), &bits, sizeof bits);
        ++received;
    }
    if (cmd_fire) accepted = true;
    if (in_fire) ++sent;

    sim->tick(); // 上升沿实际执行已采样的握手

    if (task_complete) {
        if (!accepted || sent != input_beats || received != result_count || !core.cmd_ready)
            return recover(sim, BNN_EIO);
        /* 核心已回 IDLE；不在最后结果握手同沿发新命令 */
        core.cmd_valid = 0;
        core.in_valid = 0;
        core.eval();
        sim->flush_trace();
        return BNN_OK;
    }
}
return recover(sim, BNN_ETIMEOUT);

verilator-bnn-bridge.cpp · 失败恢复C++
static BNN_Status recover(BNN_RtlSim* sim, BNN_Status status) noexcept {
    try {
        ContextScope scope(&sim->context);
        sim->reset();
        sim->flush_trace();
    } catch (...) {
        return BNN_EIO;
    }
    return status;
}

复位后模型回到 idle，下一个任务可以继续使用同一个设备。核心无取消通知；外层必须清掉旧输入源并作废该任务已写出的部分结果，不能等待旧任务的 res_last。

6.4

超时、上下文与波形

周期预算 timeout

默认预算是 input_beats + result_count + 64。预算耗尽还没完成 res_valid && res_ready && res_last 握手，桥接层复位模型、作废部分输出并返回 BNN_ETIMEOUT。这是外层软件错误码，不是核心错误通道。专项测试会故意传 max_cycles=1 触发超时，然后立刻再跑一个正常任务，确认恢复有效。

异常不穿过 C ABI noexcept

桥接函数的边界不抛 C++ 异常：std::bad_alloc 映射为 BNN_ENOMEM，其他异常映射为 BNN_EIO。结果数量、组号或边界异常也由桥接层检测并报告；核心没有运行时错误码或结果错误位。恢复路径会复位模型，避免把半完成状态留给下一个任务。

宿主上下文 ContextScope

Verilator 用线程局部存储保存当前 VerilatedContext。桥接层在 create/destroy/execute/recover 期间临时安装本设备的 context，退出时恢复调用者原来的上下文和时间。嵌入到其他 Verilator 程序时不会污染宿主状态。

波形开关 VCD

BNN_RTL_TRACE_DIR 在创建设备时读取。设为已有可写目录，就为每个设备生成一个唯一的 bnn-core-XXXXXX.vcd；目录不存在则 BNN_EIO。每次任务结束或超时恢复后 flush，关闭设备时结束文件。

verilator-bnn-bridge.cpp · 保存/恢复宿主 contextC++
class ContextScope {
    VerilatedContext* previous;
public:
    explicit ContextScope(VerilatedContext* current = nullptr)
        : previous(Verilated::threadContextp()) {
        if (current != nullptr) Verilated::threadContextp(current);
    }
    ~ContextScope() { Verilated::threadContextp(previous); }
};

这样切的收益，以及它没有解决的问题

把后端选择放在构建期，换来的是零运行时开销和清晰的边界；代价是两套工具链、两个归档，以及仿真速度与真实硬件性能之间的巨大差距。

用 ACCE=soft，当……

  • 你在跑日常回归、CI 或 Python reference 校验，想要最快速度。
  • 你只需要验证模型/引擎逻辑，不关心 RTL 时序。
  • 你希望嵌入程序用纯 C 工具链链接，依赖最少。
  • 你需要一个与硬件实现逐字节对齐的数值参考。

用 ACCE=verilator，当……

  • 你要验证 RTL 与公共 API 的接口、握手和结果顺序。
  • 你想抓 VCD，逐周期观察命令、共用输入握手、结果和最后结果握手完成事件。
  • 你在改 bnn-hw/bnn_core，希望整条推理链路立刻跑起来。
  • 你能接受明显更慢的仿真速度，并且不需要 DMA/总线模型。

当前仿真后端刻意没有做的事

×
没有总线、DMA 和存储带宽模型。桥接层直接写模型端口，一拍送一对操作数；真实设备上的访存延迟、突发传输和带宽瓶颈都不在模型里。
×
没有设备侧激活缓存。每个输出通道都重放同一组激活，导致 input_beats = (K/32) × N。真实加速器应在本地缓存激活，避免重复主机上传。
×
没有命令队列。核心是单在途任务；GEMM 的每一行都是一次独立命令，必须等上一行最后结果握手返回 IDLE，下一上升沿才能接命令，不支持同沿接新命令。吞吐不代表实际硬件。
×
RTL 只覆盖整数点积。FP16 scale 解码、乘法和有序 FP32 累加仍在 CPU，因此“上板后”的浮点后处理位置还需要在系统设计中重新决定。
×
不能在同一进程里运行时切换。两套实现导出同名符号，构建期只能选一个。想要对比，就构建两个可执行文件或两个归档，分别运行。
×
仿真时间不是性能。10 ns 是为了 VCD 可读性设定的仿真周期，与综合后的时序、面积、功耗无关。

接收方 ready 为低，发送方必须保持数据不变，不能丢拍或提前推进。
VCD
值变化转储文件，可用 GTKWave 打开，查看每个周期的信号波形。
FP16 / FP32
IEEE-754 半精度/单精度浮点。scale 以 FP16 存储，后处理要求精确转成 FP32。
TLS
线程局部存储。Verilator 用它保存当前 VerilatedContext，桥接层需要保存/恢复。
W1A8
权重 1 bit（±1），激活 8 bit（int8）。整数点积可用 32 lane 并行计算。
差分测试
同一组输入分别跑两个实现，比较输出；这里精确到字节和浮点位模式。
